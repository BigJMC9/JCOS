# Console capture

JA OS sends terminal/diagnostic output to COM1 from kernel serial initialization
onwards. Capture bytes on the host instead of transcribing screen photographs.
A host log includes boot output, commands echoed by JA OS, test results and
expected fault injections. Earlier UEFI-only screen output is not included.

## Physical machine to Windows

Connect the target's UART to a second computer through the appropriate serial
hardware. The GIGABYTE Z390 GAMING X has an internal COM header; use a bracket
matching the motherboard pinout and a compatible RS-232 connection to the
capture host (typically a null-modem connection and a USB-to-RS-232 adapter).
The capture program's COM number is the host adapter's port, not necessarily COM1.

From Windows PowerShell 5.1 in the checkout, list ports:

~~~powershell
powershell.exe -NoProfile -File tools/capture_serial.ps1 -ListPorts
~~~

Start recording before booting the target, replacing COM3 with the host port:

~~~powershell
powershell.exe -NoProfile -File tools/capture_serial.ps1 -Port COM3 -OutputPath build/rx570-serial.log
~~~

Settings are **38400 baud, 8N1, no flow control**. Received bytes are written
unchanged, including CR/LF and terminal escape sequences. The file is flushed
after each received chunk. The tool refuses to overwrite an existing log or
metadata file, and records capture metadata in a separate .log.json file.

Typed keys are forwarded when run in an interactive console. Enter sends LF;
Escape, Backspace, arrows, Home/End and Delete are supported. Ctrl+] stops
capture. With redirected input or -NoInput, use Ctrl+C or -DurationSeconds.
The raw file contains received bytes only; host status text is kept separate.
-SendLine can send a command to an already-running target; it does not wait
for boot readiness.

Run these commands over serial after boot:

~~~text
monitor
serialinfo
displayfirmware
displayprobe
test display-probe
serialinfo
~~~

Keep the raw .log and .log.json files with the flashed image hash and platform
details. Local keyboard commands plus serial output establish capture only;
entering commands from the capture host also exercises input/control. Native
GPU failure independence still requires its own physical acceptance run.

not disrupted. Native recovery and other connections/platforms require their

## QEMU

The existing run targets now save one timestamped COM1 log per launch while
keeping terminal input/output:

~~~sh
make -f Makefile.msys2 run-headless BUILD=build/rx570-capture-v5
~~~

The launcher prints the log path. Set JCOS_SERIAL_LOG to an unused filename
to choose a destination. Filenames generated by default use UTC. The file
contains guest COM1 bytes; it does not contain the launcher's status messages.

Alternatively expose COM1 through a local TCP endpoint and use the same Windows
capture tool:

~~~text
-chardev socket,id=jcserial,host=127.0.0.1,port=4444,server=on,wait=on -serial chardev:jcserial
~~~

~~~powershell
powershell.exe -NoProfile -File tools/capture_serial.ps1 -TcpHost 127.0.0.1 -TcpPort 4444 -OutputPath build/qemu-serial.log
~~~

## UART transmit limits

The kernel waits for transmit readiness under a fixed 65,536-attempt budget
rather than discarding a byte on the first busy observation. The readiness
check and one-byte write are atomic under the current UP profile; the caller's
interrupt state is restored between retries. After a timeout, further unavailable
bytes are counted and dropped promptly until readiness is observed again.
There is no unbounded wait on a failed UART.

The monitor's serialinfo command reports transmitted/dropped bytes, timeout
count and stalled status. Counts describe local UART writes, not receipt by the
other machine. Zero drops does not prove cable correctness or complete capture.
The retry budget is an iteration bound, not a measured real-time guarantee.
Serial transmission can reduce console throughput to the configured baud rate.

## Saving on the JA OS drive

The current native AHCI block devices and FAT32 implementation are read-only.
Shell redirection to a persistent boot-drive file is not implemented. A file
in RAM alone would not survive reboot or solve extraction from the target.
This capture workflow writes to the other computer and requires no filesystem
writes from JA OS. Direct on-target persistent logging remains separate storage
work.

## Validation and references

~~~sh
make -f Makefile.msys2 test-serial
make -f Makefile.msys2 test-serial-capture
~~~

The UART test links the actual kernel writer with port doubles and exercises
delayed readiness, bounded stalls, subsequent drops, recovery and CR/LF.
The Windows tool tests use TCP to verify received-byte preservation, LF command
sending, timeout completion, no-overwrite behavior and error cleanup. These are
host tests, not physical serial qualification.

See [GIGABYTE specifications](https://www.gigabyte.com/Motherboard/Z390-GAMING-X-rev-10/sp)
and the [motherboard manual](https://download.gigabyte.com/FileList/Manual/mb_manual_z390-gaming-x_v1_e.pdf)
for the COM header, [QEMU character backends](https://www.qemu.org/docs/master/system/qemu-manpage.html)
for logfile/TCP options, and [SerialPort byte reads](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.read?view=netframework-4.8.1)
for the host API. The UART register profile follows the
[16550-compatible TI register description](https://www.ti.com/lit/ds/symlink/tl16c550c.pdf).
